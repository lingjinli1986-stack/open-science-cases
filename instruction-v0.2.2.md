# Open this case in Open-Science Desktop
Version 0.2.2

Use the case page and research package linked in the user's message. The goal is to show that case's archived conversation on the user's desktop. Use the user's language for any handoff. Keep their projects, credentials and security settings intact. Keep the user in the receiving chat until their participation is actually needed.

**Order:** prepare the installed desktop → finish first-time setup → bind the requested subscription and read back the saved Main model → import once → show the new conversation on the desktop. A blocked setup pauses the task before import.

## 1. Prepare the desktop
Identify the platform and CPU. Check the [AIPOCH stable download page](https://aipoch.com/open-science/download) for the matching desktop installer. Check the installed app, not old downloads, cached installers, Pro or testing releases. Install if missing; update an older stable install using its supported updater or matching official installer. Preserve a newer installed release and report the difference. Launch the installed desktop normally. Read the running version from About or the attached desktop service; compare it with the official stable version. Record both, including any discrepancy.

Use the desktop's own backend and profile for all subsequent CLI commands. Check status and desktop attachment. On macOS the bundled CLI is backend/cli.mjs run by node-runtime/node inside the app's Contents/Resources. On Windows use the installed command or the launcher identified by the installed release. Quote paths and pass each argument separately. A separate headless start can use the wrong service or disappear when the agent command ends. Avoid starting a second service for this desktop task.

If the desktop has just launched, wait for readiness and retry a read-only status check once after a timeout. If the service is stopped, use the desktop's Retry/Reconnect control when available. On Windows, a PID that vanishes, repeated loopback timeouts, or a blocked UI launch calls for checking whether the app is running in the user's interactive desktop. If launch is blocked, ask the user to open the installed app from Start. Keep managed network and process protections in place. If the desktop service remains unreachable, report the error and stop before import rather than repeatedly launching services, creating scheduled tasks or clearing staging files.

## 2. Finish setup on this desktop profile

Work on the local Open-Science instance that will receive the package. On a new installation, use the first-run wizard. The installer itself does not choose an agent or a model. With an already configured profile, verify the same three conditions below.

Use an authorized desktop interface, or the [official local browser UI](https://github.com/aipoch/open-science/blob/v1.3.2/packages/open-science/README.md#get-started) of the **already attached service**. If your client has an approved browser tool but no desktop input tool, choose the local browser UI from the start. Use its normal visible controls. The installed CLI's `url` command provides a private local sign-in link: pass it directly on the same computer into a permitted local browser without printing it, sending it to an agent service, recording it or placing it in chat. If your tool cannot keep that link local, use the desktop or hand off. Leave process protections and permissions in place. Do not start another service, patch the installed app, call private methods or edit settings files to mark setup complete.

1. **Finish the wizard.** Continue through Environment and Data location. Keep the user's existing data location. Under Agent runtime, select the runtime for the intended plan and install or re-detect it if needed. WorkBuddy subscriptions use CodeBuddy. If the model step offers the matching subscription, configure it there. If the matching option is missing, choose Skip *on that screen only*, defer optional Notebook installation and click **Finish**. Now open Settings and complete subscription setup immediately. Verify that the wizard has closed and the workspace is available on this profile. If the native window still shows setup after completing it in the browser, resolve this before import. Use normal relaunch only if safe for active research.
2. **Bind the plan.** Respect an explicit plan. Otherwise, when WorkBuddy receives a first-use request, use the user's WorkBuddy subscription through CodeBuddy. Reuse an existing compatible, ready binding when available. Determine China or International from an explicit user preference or an unambiguous matching signed-in region shown by the provider. If ambiguous, ask one short region question in chat and wait. Never infer the region from language or search chat history or credential files. In **Settings → Agent**, verify CodeBuddy is active. In **Settings → Model → Add provider**, choose the matching CodeBuddy subscription. Use existing CodeBuddy CLI sign-in only when it is ready for that same region. Otherwise choose **Sign in with Open-Science → Sign in with browser**. Keep this one sign-in request pending while the owner authorizes on the provider's page. Wait for the matching subscription and its model list to appear in OS. Keep login credentials and authorization URLs private.
3. **Set and read back Main model.** In **Settings → Model → Main model**, select an entry from the authorized subscription's list. Use the user's supported preference, or the provider's recommended/default listed model. If no preference or default exists, offer a listed option and ask only if the choice cannot be resolved. Reopen the setting and read back the model name **and its provider/region**. A Kilo Gateway default after Skip or after adding CodeBuddy still requires changing Main model. Run `open-science doctor --json` on the attached instance to check readiness. Use configuration and login status only. Never send a model message just to open a case.

For Codex, use the compatible Codex framework and requested Codex subscription. For Claude Code, select a Claude subscription only where the active framework offers it. For OpenCode, choose an actually supported, authorized provider and model. The assistant that receives the request may differ from the requested plan. If a different provider is already configured and the intended plan is unclear, ask before changing it. See the [framework guide](https://aipoch.com/docs/guides/frameworks/) and [provider guide](https://aipoch.com/docs/guides/providers/).

**Before any import**, record these three observed values: (1) first-run setup finished on the target profile, (2) active runtime and ready subscription with region, (3) saved Main model paired with that subscription. Doctor should report the expected runtime and ready provider. Doctor alone does not expose the wizard state or prove the selected provider/model pair. If any value is missing, pause here, state which value is missing and give the single next action in the user's language. Resume this same request after that action. Do not download-and-import as a fallback, create a project or declare success during the pause.

## 3. Import this package once
Read the title, research-package download link and one distinctive finding or artifact from the supplied case page itself. Match the supplied package URL to that link and match the case to the [official manifest](https://statics.aipoch.com/open-science/usecases/manifest.json). Verify the downloaded file's exact byte count and SHA-256. A separate introduction file is unnecessary. Stop on a mismatch.

Choose a unique destination for this request (title plus timestamp or short suffix). On the desktop-attached CLI use the verified absolute archive path:

    open-science session import "$archive_path" --new-project "$unique_project_name" --non-interactive --json

Save the returned project ID and session ID. An earlier project with the same title is not evidence of this import. If interrupted, check this operation's progress, destination and returned IDs before any retry. A timeout may occur after import succeeds. Reuse a confirmed result from this attempt; if its outcome remains uncertain, stop and report it without creating another project. Do not browse unrelated projects or edit the database. A documented desktop-import preview is an alternative when CLI import has not already begun; use its completion action for this import and capture its IDs through supported status when available.

## 4. Bring OS forward and display this conversation
After successful import, request normal activation of the installed desktop. On macOS use the registered open-science://open handler (for example, open 'open-science://open'); on Windows use the registered handler via the normal desktop shell, or activate the existing Open-Science window with an authorized desktop tool. The bare URI activates the app; it has no session-ID argument. Check the foreground application/window separately from whether a process exists. Do not claim foreground when the desktop session cannot be observed.

If the completion dialog offers **Open imported Session**, use that button first. Otherwise select this attempt's exact project and session. A single-session project may open the transcript immediately. Confirm the visible transcript against the saved case detail and returned IDs where exposed. A process, an import receipt, a project list, an MCP lookup or a web replay alone does not prove desktop visibility.

Use only desktop capabilities already permitted to this agent on this host. WorkBuddy was denied System Events on one Mac; use the actual permission result on each host. After a denial, stop attempting alternative UI automation. If you cannot inspect the window, clearly label the following UI choices as conditional instead of claiming which screen is visible. If OS is already in front and shows the completion dialog, say “案例已导入，请点「Open imported Session」。” If it shows Projects, give the unique project name and, only if necessary, the session to select. If foreground cannot be confirmed, tell the user to select OS in the Dock or taskbar first and record this extra step separately. If onboarding is still visible, give the remaining setup steps; do not promise one click. Report the running version, account readiness, IDs, observed foreground and transcript, and exactly what still needs the user's action.
